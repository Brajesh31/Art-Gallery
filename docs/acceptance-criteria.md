# ✅ Acceptance criteria and definition of done

## Documentation changes
- [ ] The guide has a clear purpose and scope.
- [ ] It distinguishes implemented features from proposals.
- [ ] Links resolve to real repository files.
- [ ] Diagrams match the current static architecture.
- [ ] No fake demo URLs, screenshots, test results, or asset credits are included.

## HTML/CSS changes
- [ ] All three pages open directly.
- [ ] Local image, stylesheet, and script paths resolve.
- [ ] Navigation destinations are correct.
- [ ] Responsive behaviour is checked.
- [ ] Keyboard focus is visible.
- [ ] Images have suitable alt text.
- [ ] Browser console errors are reviewed.

## Artwork changes
- [ ] Source and redistribution rights are verified.
- [ ] Attribution requirements are recorded.
- [ ] Alt text describes the actual image.
- [ ] File dimensions, size, and format are reviewed.
- [ ] EXIF metadata is checked.
- [ ] Existing asset references are preserved or updated.

## Dependency changes
- [ ] Purpose and usage are documented.
- [ ] Version is pinned.
- [ ] HTTPS is used.
- [ ] Integrity metadata is verified against exact bytes where supported.
- [ ] Privacy and availability implications are reviewed.
- [ ] All affected pages are tested.

## Release definition of done

A release is ready only after automated repository checks pass, manual page checks are recorded, external resources have been reviewed, image rights are understood, and the exact deployed commit has been smoke-tested.
